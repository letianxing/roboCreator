# 自主表演与编排备用模式

状态：架构草案；用户确认自主对打优先、编排模式兜底。未训练策略，未完成实时性验证。

## 分层设计

1. 状态估计：融合关节、躯干 IMU、可用接触信息；视觉提供对手及环境观测，音频用于交互或触发候选。
2. 行为决策：在已验证的动作集合内选择靠近、姿态展示、出招、躲避、躺下、起身等。动作是否保留由机械能力与实测决定。
3. 动作执行：带进入条件和退出条件的控制器/策略完成动作；禁止在不兼容姿态间直接切换。
4. 本地运行监控：限制位置、速度、电流/力矩、温度和通信超时，处理失衡、故障及停止。具体硬件反馈项与限值待选型。

## 模式及降级

- 自主模式：基于对手观测选择并执行允许的动作；需要评估遮挡、误检、观测时延与动作不可撤销区间。
- 编排模式：由人工或程序触发验证过的动作序列；同样需要状态检查，不绕过底层限值。
- 自主不可用但机器人状态正常时：先完成受控转换，再进入等待或编排模式。
- 视觉丢失、碰撞异常、失衡或通信故障时：按状态进入稳定、停止或恢复流程，不将攻击套路用作故障降级动作。
- 倒地恢复：确认姿态、接触和关节状态后选择恢复路径，失败时停止重试并记录原因；具体重试次数待试验确定。

## 算力划分约束

AutoDL 用于训练，不默认作为真机实时平衡或关节控制节点。关节控制、运行保护和必要的状态估计应在机器人本地运行。

用户已确认允许旁路电脑运行模型，板载执行“小脑”与上位机指令。须实测端到端时延/抖动和断网降级；不能假定家庭 Wi-Fi 满足实时控制需求。

### 初步接口边界

- 电脑侧：视觉处理、交互、高层行为选择、编排及日志分析；展示电脑硬件待确认。
- 板载计算侧：机器人状态估计、动作执行和需要的运动策略推理；可部署性由实际模型耗时和硬件资源验证，不默认普通 MCU 能运行完整运动策略。
- 实时执行/驱动侧：关节采样、执行器通信、控制调度、限值和看门狗。是否需要独立 MCU 根据选型确定，不等同于必须新增三块主板。
- 上位机命令拟包含 robot_id、sequence、时间/有效期、模式、动作或运动目标与参数；需要状态确认和拒绝原因，不假定每次发送都成功执行。
- 机器人返回时间戳、模式、状态估计、关节/电源/温度可用反馈、动作阶段与故障信息。双方时间同步方式待设计。
- 视频从相机经机器人侧采集后上传电脑；USB 相机不能直接凭 Wi-Fi 连到上位机，须计算采集、压缩、带宽、功耗和延迟。如使用深度数据，进一步验证传输形式与标定一致性。
- 网络中断时禁止继续接收过期命令，根据当前姿态与动作阶段进入本地稳定/受控停止。不能一律立刻卸力，以免支撑状态下倒地。
- 底层关节闭环不依赖逐帧无线指令；频率与时延预算尚待计算和实测，当前不虚构数值。

## 训练与验收

先验证基础动作和恢复，再加入对手观测与自主选择。分别测量对手检测/跟踪、决策正确性、反应时间、动作完成、恢复成功和异常处理；编排成功不能证明自主对打成功。

训练对手多样性、未知动作泛化和相机实测差异需单独验证。能力仍以现有预算和物理硬件为界，不承诺通过 RL 补偿不足的驱动、活动范围或传感信息。
